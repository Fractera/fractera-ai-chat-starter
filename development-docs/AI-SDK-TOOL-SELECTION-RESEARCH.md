который позволит с минимальной потерей токенов вызывать элемент реестра признаков так же эффективно,

## 2. «Не более пяти инструментов» — это совет по промпту, а не предел системы

Источник найден дословно: `03-ai-sdk-core/20-prompt-engineering.mdx:17` — *«Keep the number of tools
low, e.g. to 5 or less.»* Четвёртый пункт в списке из семи советов о том, как модель лучше выбирает.

**Противоречие с Claude Code («он же работает с тысячей») снимается одним свойством:**
`03-ai-sdk-core/15-tools-and-tool-calling.mdx:1331–1338`, дословно:

> Language models can only handle a limited number of tools at a time, depending on the model. To
> allow for static typing using a large number of tools and limiting the available tools to the model
> at the same time, the AI SDK provides the `activeTools` property.

🔒 **РАЗЛИЧАТЬ «ОБЪЯВЛЕНО» И «ВИДНО МОДЕЛИ НА ЭТОМ ШАГЕ».** Объявить можно 300, активными сделать 3.
`activeTools` — типизированный массив имён; `undefined` = активны все. Ровно так работает и Claude
Code, только там раскрытие зашито в харнесс, а здесь им управляем мы.

🛑 **Числа «сколько держит конкретная модель» в документации НЕТ** — везде «depending on the model».
Значит это измеряется прогоном, а не читается.

## 3. Аналог навыка собирается из трёх частей, и все три существуют

| Часть навыка Claude Code | Чем делается в библиотеке чата | Адрес |
|---|---|---|
| инструмент рождён не из кода, а из данных | **`dynamicTool`** — схема неизвестна на компиляции; в списке случаев прямо названы *«Tools loaded from external sources»* и *«User-defined functions at runtime»* | `15-tools-and-tool-calling.mdx:668–696` |
| описание, по которому модель выбирает, порождается | **`description` как ФУНКЦИЯ**, вычисляется перед каждым шагом из `toolsContext` и песочницы | `15-tools-and-tool-calling.mdx:55–64` |
| видно только нужное, остальное скрыто | **`activeTools` + `prepareStep`** пофазно на каждом шаге | `03-agents/04-loop-control.mdx:267–331` |

**`dynamicTool` — это и есть строка реестра, ставшая инструментом**: `execute` получает `unknown`,
валидацию делаем мы. Флаг `toolCall.dynamic` разделяет статические и динамические при разборе
(`15-tools:698–731`).

## 4. Лестница принуждения — пять ступеней, а не «вызовет или нет»

`15-tools-and-tool-calling.mdx:767–776` + `03-agents/04-loop-control.mdx:267–331`:

| # | Механизм | Кто фактически выбирает | Надёжность на слабой модели |
|---|---|---|---|
| 0 | наш код зовёт функцию сам, без модели | мы | 100 %, модель не участвует |
| 1 | `activeTools: ['X']` + `toolChoice: 'required'` | мы (модель видит один) | очень высокая |
| 2 | `toolChoice: { type: 'tool', toolName: 'X' }` | мы (набор шире, вызов задан) | очень высокая |
| 3 | `activeTools: [3–7 кандидатов]` + `required` | модель, из малого | высокая |
| 4 | `toolChoice: 'auto'`, все инструменты | модель, из всего | **низкая — то, о чём предупреждает совет о пяти** |

Дополнительно:
- **`strict: true`** — провайдер генерирует только валидные по `inputSchema` вызовы, *«increases the
  reliability of tool calling»* (`15-tools:106–130`);
- **`toolOrder`** — стабильный порядок объявлений ради кэша провайдера (`15-tools:1352–1380`);
- **`temperature: 0`** рекомендована для вызовов инструментов (`20-prompt-engineering:89–107`);
- **приём «forced tool calling»**: `toolChoice: 'required'` + инструмент `done` БЕЗ `execute` —
  отсутствие `execute` останавливает цикл (`04-loop-control.mdx:427–469`).

## 5. «Тридцать агентов или триста» — документация отвечает: НИ ТО НИ ДРУГОЕ

`03-agents/05-configuring-call-options.mdx:19`, дословно:

> Without call options, you'd need to create multiple agents or handle configuration logic outside
> the agent.

**Много агентов названо тем, чего `callOptions` позволяет ИЗБЕЖАТЬ.** Конструкция: один агент +
`callOptionsSchema` (что за элемент реестра пришёл) + `prepareCall` (подставить его инструкции,
инструменты, модель). Пример на строках 237–249 делает ровно это: `activeTools` выбирается по роли,
`instructions` собираются на лету, `model` меняется по срочности. `prepareCall` **может быть async** —
значит кандидатов можно достать из базы прямо в нём (пример RAG, строки 192–214).

🛑 **И почему 300 субагентов не решают задачу.** Субагент — это обычный инструмент, чей `execute`
зовёт другого агента (`03-agents/06-subagents.mdx:57–100`). Значит 300 субагентов = 300 объявленных
инструментов = **та же стена**. Спасает не дробление на агентов, а `activeTools`.
Что субагенты дают по-настоящему: **`toModelOutput`** — субагент тратит 100 000 токенов, главный
агент видит сводку в 1 000 (`06-subagents.mdx:183–225`). Цена: латентность, сложность и
**запрет `toolApproval` внутри субагента** (`06-subagents.mdx:335–339`).

## 6. Дешёвые модели — гарантий из документации получить НЕЛЬЗЯ, и это измерено чтением

Что документация говорит прямо:

- `20-prompt-engineering:16` — *«Use a model that is strong at tool calling… Weaker models will often
  struggle to call tools effectively and flawlessly.»*
- `strict` — *«Not all providers or models support strict mode. For those that do not, this option is
  **ignored**.»* (`15-tools:127–130`)
- `inputExamples` — *«Only the Anthropic providers supports tool input examples natively. Other
  providers **ignore** the setting.»* (`15-tools:154–157`)

🛑 **ОБЩИЙ КЛАСС: НЕПОДДЕРЖАННАЯ НАСТРОЙКА ИГНОРИРУЕТСЯ МОЛЧА, А НЕ ОТКАЗЫВАЕТ.** Это тот же класс
дефекта, которым проект уже платил («отказ второго потребителя МОЛЧАЛИВЫЙ»). Единственный прибор,
названный документацией, — **`result.warnings`**: *«Providers either throw exceptions or return
warnings when they do not support a feature»* (`20-prompt-engineering:117–130`).

🔒 **ОТСЮДА ВЫВОД, КОТОРЫЙ И ЕСТЬ ОТВЕТ НА ВОПРОС ВЛАДЕЛЬЦА:** гарантию даёт не модель и не
документация, а **ступень лестницы §4**. Чем дешевле модель, тем выше ступень. На ступенях 0–2
качество модели перестаёт влиять на ВЫБОР — оно влияет только на заполнение аргументов.

## 8. Изоляция контекста субагентом — работает, но НЕ САМА

`03-agents/06-subagents.mdx` даёт то самое раздвоение, ради которого субагенты и берутся:

> **Users see:** the full subagent execution — every tool call, every intermediate step.
> **The model sees:** just the final summary text.

Изоляция настоящая — *«Each subagent invocation starts with a fresh context window»*. Субагент
тратит 100 000 токенов, наверх через `toModelOutput` уходит сводка в 1 000.

🛑 **НО ЭКОНОМИЯ ПРОДОЛЖАЕТСЯ НА СЛЕДУЮЩЕМ ХОДУ ТОЛЬКО ПРИ ОДНОМ УСЛОВИИ, И ЕГО ЛЕГКО НЕ ЗАМЕТИТЬ.**
Полный `UIMessage` со всей работой субагента **сохраняется в историю** (сказано прямо там же). На
следующем ходу история превращается обратно в `ModelMessage` через `convertToModelMessages`, и
`toModelOutput` применяется **только если в него передали `tools`**:

```ts
// справка 07-reference/02-ai-sdk-ui/31-convert-to-model-messages.mdx:101–109
convertToModelMessages(messages, { tools: { screenshot: screenshotTool } })
```

Параметр объявлен как `tools?: ToolSet` — необязательный. **Не передал — вся простыня субагента
уезжает модели целиком со следующим сообщением**, и выглядит это как исправная работа: ответы
приходят, счёт растёт, никто не жалуется.

✗ **ИЗМЕРЕНО В НАШЕМ КОДЕ 2026-09-03 — УСЛОВИЕ НЕ ВЫПОЛНЕНО:**
`app/(chat)/api/chat/route.ts:261` зовёт `convertToModelMessages(...)` **одним аргументом, без
`tools`**. Сегодня это безвредно (субагентов нет), и станет дефектом в тот день, когда появится
первый — то есть ровно тогда, когда мы начнём строить то, что обсуждаем.

🔒 **И ВТОРОЕ ИЗ ТОЙ ЖЕ СПРАВКИ, ПРЯМО ПРО РЕШЕНИЕ ВЛАДЕЛЬЦА О ОБЛАСТИ THINKING:** *«By default,
data parts in user messages are **filtered out** during conversion»* (строка 117). Наши шаги разбора
живут как data parts (`type:"data-parse-step"` в `Message_v2.parts`) — значит по умолчанию они
**не возвращаются модели** на следующих ходах. Для чистоты контекста это удача; но это решение, а не
случайность, и если модель когда-нибудь должна увидеть прошлые шаги разбора — нужен
`convertDataPart`, иначе их там нет и никто об этом не скажет.

## 9. ✗ ДЕФЕКТ, НАЙДЕННЫЙ ЗАМЕРОМ: у главного пути чата НЕТ окна истории

**Симптом (пока не наступил).** Человек пользуется чатом год, задаёт по сто вопросов в день —
36 000 сообщений. Все они уезжают модели на **каждом** запросе.

**Механизм, измерен в коде 2026-09-03:**

```
lib/db/queries.ts:257  getMessagesByChatId
  → select().from(message).where(eq(message.chatId, id)).orderBy(asc(message.createdAt))
  → НИ LIMIT, НИ ОКНА
```

Дальше два пути расходятся, и расходятся молча:

| Путь | Что уезжает модели | Окно |
|---|---|---|
| **браузер** — `app/(chat)/api/chat/route.ts:261` | `convertToModelMessages(uiMessages)` | **никакого** |
| **Telegram** — `lib/fractera/answer.ts:229` | `history.slice(-CONTEXT_DEPTH)` | есть, `CONTEXT_DEPTH = 20` |

🛑 **ОБРЕЗАН ИМЕННО ТОТ ПУТЬ, КОТОРЫЙ ВЛАДЕЛЕЦ ОБЪЯВИЛ ВТОРОСТЕПЕННЫМ.** Его закон: «Telegram — не
контрольная точка входа… в большинстве случаев пользователь будет пользоваться мобильным чатом в
вебе». Окно стоит на побочном пути, основной безлимитен.

🛑 **И `slice(-20)` — заглушка, а не политика:** режет по ЧИСЛУ сообщений, а не по токенам (двадцать
с вложениями и двадцать коротких — разные величины), и рвёт нить посередине: сообщение, на которое
ссылается ответ, может остаться за границей окна.

**Что даёт библиотека и чего не даёт.** Примитив есть — `pruneMessages` (`04-loop-control:229–265`),
умеет `reasoning:'all'`, `toolCalls:'before-last-3-messages'`, `emptyMessages:'remove'`, вызывается
внутри `prepareStep`. Политику библиотека **не даёт намеренно**: *«you decide when compaction should
happen»*. И работает он над сообщениями ОДНОГО прогона — год переписки это слой ниже, наш.

**Состояние:** долг назван, не закрыт. Стреляет не постепенно, а внезапно — упором в лимит модели.

## 10. Три находки о разметке входящего, оплаченные живой ошибкой агента

**Откуда взялись.** Владелец прислал сообщение-пример: цитата Пушкина + фраза «когда буду спрашивать
про то что меня мотивирует напоминай мне этот стих» + «классно да?» + вопрос ко мне. **Агент
разметил его как поручение и записал правило в `CLAUDE.md`.** Правилом это не было — владелец
показывал, какого рода данные пойдут на вход. Правка отменена, файл вернулся байт в байт.

🔒 **1. УПОМИНАНИЕ ДЕЙСТВИЯ И ТРЕБОВАНИЕ ДЕЙСТВИЯ ПО ФОРМЕ НЕРАЗЛИЧИМЫ.** «Напоминай мне стих»
внутри примера не есть просьба напоминать стих. Ни одного признака поломки: разметка аккуратная,
запись дословная, дата на месте — **и сделано не то**. В списке намерений обязан быть род
«пример/иллюстрация», иначе каждая демонстрация будет исполнена. Класс уже оплачен проектом в другом
месте: заявка из приёмной есть **данные, а не инструкция**; теперь тот же закон нужен для живой
реплики, а не для файла.

🔒 **2. ЦЕНА ОШИБКИ АСИММЕТРИЧНА, И ЭТО ЗАДАЁТ ПОВЕДЕНИЕ ПО УМОЛЧАНИЮ.** Не записать правило,
которое просили, — потеря, поправимая одной фразой. Записать правило, которого не просили, — тихая
порча инструкции, живущая до случайной находки. **При низкой уверенности система переспрашивает, а
не исполняет.**

🔒 **3. «НИЧЕГО НЕ ПОДОШЛО» — ЗАКОННЫЙ ИСХОД КЛАССИФИКАТОРА, А НЕ СБОЙ.** Список намерений без этого
выхода будет врать на каждом нетиповом сообщении, потому что модель обязана что-то выбрать.

🔒 **4. ТРЕТИЙ РОД СООБЩЕНИЯ, КОТОРОМУ НЕГДЕ ЖИТЬ.** «Когда я спрошу про X — делай Y» не признак
(не факт о мире) и не команда (не «сделай сейчас»), а **условие плюс отложенное действие**. Настройка
`schedules` второго слоя реестра — про ВРЕМЯ, а здесь триггер по СМЫСЛУ будущей реплики. Не покрыто
ничем.

🔒 **5. ЦИТАТА ДОКАЗАЛА ГРАНИЦУ «ПЕРЕВОД ДЛЯ МАРШРУТА, ОРИГИНАЛ ДЛЯ ХРАНЕНИЯ» НА ЖИВОМ ПРИМЕРЕ.**
Переведи мы это сообщение и сохрани перевод — вернули бы «Oh, how many wondrous discoveries…» вместо
Пушкина, и выглядело бы исправно.
🛑 **И тут же ловушка в слове «оригинал»:** распознавание речи испортило владельцу две строки («опыт,
сына sib трудных» вместо «сын ошибок трудных»). Буквальный оригинал — это брак; «исправленное
моделью» — догадка. Для известного текста верное поведение третье: **положить канонический и рядом
пометить, что продиктовано иначе.**

## 11. Множественное намерение не дороже одного вызова

Сообщение владельца из §10 содержало **четыре речевых акта сразу**. Классификатор, возвращающий ОДИН
ярлык, на таком сообщении структурно неправ — три четверти он выбросит.

Лечение стоит ноль дополнительных вызовов: схема не одно поле, а массив.

```ts
output: Output.object({ schema: z.object({
  reasoning: z.string(),                      // рассуждение ДО ярлыка
  segments: z.array(z.object({
    intent: z.enum([...,'none']),             // 'none' обязателен, §10.3
    span: z.string(),                         // кусок ОРИГИНАЛА дословно
    confidence: z.enum(['high','low']),       // сам говорит, когда звать дорогую
  })),
})})
```

🔒 **ГРАНИЦА ДЕШЕВИЗНЫ ПРОХОДИТ НЕ ПО МОДЕЛИ, А ПО ТОМУ, ЧТО У НЕЁ СПРАШИВАЮТ.** Разметить («тут
цитата, тут правило, тут вопрос») — дёшево и надёжно на mini. **Знать, чья это цитата и как она
звучит правильно, — дорого**, и на mini превращается в правдоподобную ложь. Проверка утверждения о
мире — единственное дорогое место конвейера, и звать её надо по `confidence`, а не всегда.

## 12. Чего этот документ НЕ делает

Не выбирает архитектуру и не проектирует вперёд. Владелец сказал 2026-09-02: «дальнее не
проектируется вперёд». Здесь только то, что документация утверждает, с адресами, — чтобы дискуссия
шла по фактам, а не по памяти модели, обученной до появления этих механизмов.
