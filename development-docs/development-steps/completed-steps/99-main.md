## Что теперь умеет система

Служба `:3500` держит **список** ботов вместо одного токена: у каждого свой цикл опроса, свой
счётчик обновлений (`offset`), своя привязка. Двери принимают адресата (`bot`) и без него падают на
первого — старый однобутовый конфиг переезжает в список сам при первом чтении, ничего не ломая.
На экране `/{lang}/architect/telegram` — аккордеон, по строке на бота, кнопки «добавить» и «убрать».
Разговор каждого бота — свой `Chat` с `channelChatId`, выведенным из `telegram:<chat_id>`: сколько бы
ботов ни подключилось, каждый живёт в своём разговоре и не путается с чужим.

> из них создаст просто свой чат и будет всегда оставаться внутри своих чатов.»

## Ошибки — три, все найдены измерением, а не догадкой

1. **`offset = 0` присваивался удалённой переменной.** Синтаксис ошибку не показывал: присваивание
   заводило посторонний глобальный `offset`, а цикл продолжал читать старый. Смена токена не
   сбрасывала счётчик, и новый бот терял первые сообщения. Дефект внесён мной же часом раньше, в
   99-2.
2. **Код привязки не помнил своего бота.** Со вторым ботом привязка одного закрывала бы привязку
   другого — `pendingLinks` была общей картой без ключа-адресата.
3. **Остальные двери службы читали только старую (одиночную) форму конфига.** С появлением списка
   они разом ответили бы «бот не настроен» — молча, без исключения.

## Что осталось долгом

- **доказательство на ДВУХ живых ботах одновременно недостижимо агентом**: второй токен выдаёт
  только @BotFather. Проверено полным циклом на одном боте: добавление → список из двух записей →
  отказ `404` на несуществующего → удаление → первый цел. Второй живой токен подтверждает владелец
  вживую, а не агент;
- **приватность графа знаний и векторов между разными ботами** — по слову владельца «сейчас не
  обсуждается», не спроектирована;
- **логика ответа не входила в этот шаг** — построена отдельно, шагом 97 (97-9, 97-10), в тот же
  день.
