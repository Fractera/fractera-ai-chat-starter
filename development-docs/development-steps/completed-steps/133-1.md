# Подшаг 133-1 — три двери хранилищ измерены живьём. Две работают, третья молча падает

**Цель подшага:** снять предположение, отвечают ли `remember`, `learn` и `/media/upload` под
нынешним ключом и в защищённом режиме. Пока это не измерено, остальные семь подшагов стоят на догадке.

## Что измерено

Ключ слоя данных найден (`DATA_SECRET`, 64 символа, у слота). Все три двери ведут в `:3300` с
заголовком `X-Data-Secret` — это подтверждено чтением `lib/fractera/data-service.ts`.

```
1) POST /vectors                      → {"ok":true,"id":"4c5438f1-…","dims":1536,
                                          "model":"text-embedding-3-small","index":"partitioned"}
2) POST /service/rag/documents/text   → {"status":"success","track_id":"insert_20260905_163050_…"}
3) POST /media/upload                 → {"ok":true,"item":{"id":"914e1961-…","url":"…/file"}}
```

✅ **Векторная память РАБОТАЕТ ПОЛНОСТЬЮ.** Обратный поиск нашёл записанное:
`{"scanned":1,"indexed":true,"results":[{"id":"4c5438f1-…","collection":"probe-133"}]}` — то есть
не только принято, но и проиндексировано.

✅ **Медиатека РАБОТАЕТ ПОЛНОСТЬЮ** — файл получил идентификатор и адрес.

## 🔴 ГЛАВНАЯ НАХОДКА: граф знаний принимает и падает

```
GET /service/rag/documents → {"statuses":{"failed":[{"content_summary":"Проба 133-1…",
                                                     "error":"'OPENAI_API_KEY'"}]}}
```

**Дверь ответила `success`, а документ ушёл в `failed`.** Обработка идёт в фоне, и отказ виден
только следующим запросом.

🛑 **ОТСЮДА ЗАКОН, КОТОРЫЙ ЭТОТ ЗАМЕР ОПЛАТИЛ: У ГРАФА ЗНАНИЙ `success` ОЗНАЧАЕТ «ПРИНЯТО», А НЕ
«СРАБОТАЛО».** Сам `learn()` возвращает `{accepted: true}` и по устройству не может знать больше:
движок строит граф позже. **Проверять надо состоянием документа, а не ответом на отправку** — иначе
приём будет выглядеть исправным при полностью мёртвом графе.

## Причина — измерена до строки библиотеки

```
lightrag/llm/openai.py:166
    if not api_key:
        api_key = os.environ["OPENAI_API_KEY"]
KeyError: 'OPENAI_API_KEY'
```

В `/opt/fractera/services/rag/.env` ключ лежит **дважды и под другими именами**:

```
LLM_BINDING_API_KEY        заполнен, 164 символа, хвост …RSIA
EMBEDDING_BINDING_API_KEY  заполнен, 164 символа, хвост …RSIA
OPENAI_API_KEY             ОТСУТСТВУЕТ
```

✅ **И это ТОТ ЖЕ ключ, что у слота** — сверено побайтно: `совпадает — ДА`.

🔒 **ТО ЕСТЬ ЭТО НЕ «КЛЮЧ НЕ ДОЕХАЛ», А «ДОЕХАЛ ПОД ИМЕНЕМ, КОТОРОГО ЭТОТ ПУТЬ КОДА НЕ ЧИТАЕТ».**
Конфигурация задаёт ключ под именами привязок; конкретная ветка библиотеки, создающая клиента
OpenAI, лезет в переменную окружения. Разница видна только тогда, когда документ уже провалился.
✗ **Это тот же класс, что дефект 110: имя переменной принадлежит ПОТРЕБИТЕЛЮ**, и знание закона его
не исполняет — здесь потребителем оказалась чужая библиотека, а не наш код.

🛑 **И ЭТО ЛОМАЕТ ЗАКОН 77-8 О ТРЁХ ПОТРЕБИТЕЛЯХ КЛЮЧА.** Плашка «ключ задан у всех живых» смотрит
на наличие значения, а не на то, читает ли его тот, кому оно предназначено. Граф отвечает
«ключ есть» и при этом не работает.

## Лечение — одна строка, и нового секрета не появляется

Добавить в `/opt/fractera/services/rag/.env`:

```
OPENAI_API_KEY=<то же значение, что уже лежит там в LLM_BINDING_API_KEY>
```

и перезапустить `fractera-rag`.

🔒 **АГЕНТ ЭТОГО НЕ СДЕЛАЛ И ЖДЁТ СЛОВА ВЛАДЕЛЬЦА.** Федеральный закон называет изменение настроек и
ключей среди того, что нельзя по своей инициативе. Значение не новое — оно уже дважды в этом файле,
— но файл с ключами боевой службы правится по его слову, а не по моему выводу.
