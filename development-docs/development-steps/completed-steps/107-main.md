## Что делали и как

Владелец сообщил, что граф знаний перестал подключаться сам, и назвал разницу: раньше он вводил ключ
в **административной панели**, теперь — на **экране Telegram-бота**. Измерение объяснило почему.

🔒 **ГЛАВНОЕ: ИМЯ ПЕРЕМЕННОЙ ПРИНАДЛЕЖИТ ПОТРЕБИТЕЛЮ, А НЕ НАМ.** LightRAG не читает
`OPENAI_API_KEY` — он читает **`LLM_BINDING_API_KEY`** и **`EMBEDDING_BINDING_API_KEY`**. Экран бота
писал первую; панель (`bridges/app/app/api/config/embeddings/route.ts:85–92`) с самого начала пишет
две правильные. **Слова владельца «раньше подключалось автоматически» подтвердились кодом, а не
догадкой.**

✗ **ЧТО БЫЛО БЫ БЕЗ ПРАВКИ.** Нажатие «Сохранить ещё раз», которое советует сам экран, дописало бы
`OPENAI_API_KEY=sk-…` в файл графа: **плашка позеленела бы, граф остался слепым**, а отказ у него
молчаливый — приём документа отвечает `200` и не встраивает ничего.

**Построено:** карта `VARS` в `lib/architect/openai-key.ts` — имена переменных объявлены как свойство
каждого потребителя. Писатель пишет **все** имена потребителя; читатель считает «задан» только когда
заполнены **все**: одна из двух у графа — это работающая генерация при слепом встраивании, то есть
тот же молчаливый отказ с другой стороны.

## Доказательство 1 — писатель, на временных файлах

**Что запущено:** `scripts/probe-openai-key-consumers.ts`, собран
`esbuild --bundle --alias:@=. --alias:server-only=<заглушка>`, исполнен `node`. Пути окружения
переопределены — в модуле это предусмотрено намеренно («чтобы работа проверялась на временной папке»).

**Дословный вывод:**
```
до записи: {"configured":false,"present":true}
writeOpenAiKey → {"written":["app","data","graph"],"failed":[]}
  ✓ LLM_BINDING_API_KEY заполнена
  ✓ EMBEDDING_BINDING_API_KEY заполнена
  ✓ НЕГАТИВНЫЙ КОНТРОЛЬ: OPENAI_API_KEY в файл графа НЕ добавлена
  ✓ граф числится среди записанных
  ✓ соседи не сломаны
```

**Что доказывает:** ключ уезжает графу под именами, которые тот читает, и **бесполезная переменная не
заводится** — зелёный цвет не покупается.
**Как выглядело бы без правки:** в файле графа стоял бы `OPENAI_API_KEY`, а обе рабочие переменные
остались бы пустыми.

## Доказательство 2 — читатель, три негативных контроля

**Дословный вывод:**
```
  ✓ после записи граф = задан
  ✓ НЕГАТИВНЫЙ КОНТРОЛЬ: половина переменных → НЕ задан
  ✓ НЕГАТИВНЫЙ КОНТРОЛЬ: один OPENAI_API_KEY → НЕ задан
```

**Что доказывает:** плашка перестала врать в обе стороны. Прежде третий случай давал **зелёный при
слепом графе** — ровно тот дефект, ради которого шаг заведён.
**Плоскость иная, чем у первого:** писатель и читатель ломаются независимо, и проверены отдельно.

задачи.

## Ошибки

1. **Первая проверка «потомок ли слушатель pm2» дала ложное «нет».** Разбирал `/proc/PID/stat`
   четвёртым полем, а в имени процесса `next-server (v1…` есть пробелы — поля сдвинулись, и я прочёл
   状态 вместо ppid. Лечение — `ps -o ppid=`. 🔒 **Ложное «нет» опаснее ложного «да»**: оно послало бы
   чинить здоровую цепочку.
2. **Прибор не собирался:** `server-only` не разрешается вне Next. Лечение — алиас на пустую заглушку,
   а не удаление импорта из рабочего кода.
3. **Область шага выросла по ходу** — владелец добавил требование «ключ может быть перехвачен в любом
   месте». Измерено: писателей **три**, и они разные. Панель пишет верно, экран архитектора чинён
   здесь, **чат не пишет графу вовсе** — это долг, названный ниже.

## 🛑 Долг, оставленный сознательно

**Чат (`fractera-chatbot-starter/app/api/fractera/openai-key/route.ts`) пишет ТОЛЬКО файл слота.**
Ключ, введённый в чате, не доедет ни до слоя данных, ни до графа — то есть ожидание владельца «в
любом месте» сегодня выполняется на две трети.

🔒 **И чинить это копированием писателя в третий раз НЕЛЬЗЯ** — именно так и родился сегодняшний
дефект: три места пишут один файл и расходятся молча. Тот же класс, которым оплачен шаг 78-6
(«два экрана из двух процессов писали ОДИН файл»). Правильная форма — **одна дверь, три звонящих**.
Заводится отдельным шагом.

## Эволюция навыков

- **`use-testing`, применено:** недостижимое доказательство (сессия владельца) названо вслух и не
  подменено. Второй раз за две сессии — раздел работает.
- **Предложение в `use-testing`:** добавить строку о **ложном отрицательном результате измерения**.
  Правило «измерение, дающее ноль, не считается измерением» написано про предмет; здесь ноль дал
  **разбор вывода** (сдвиг полей `/proc/stat`), и это отдельный род ошибки прибора.
- **`use-development-steps`, наблюдение:** требование владельца, добавленное после заведения шага,
  расширило объём вдвое. Стоит сверять объём вслух в момент добавления, а не в момент коммита.
