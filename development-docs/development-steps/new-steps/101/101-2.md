# 101-2 — та же часть на серверном пути (Telegram, без браузера)

## 1. Что строится

В `lib/fractera/answer.ts`, `answerInboundMessage()`: перед `saveMessages(...)` в массив `parts`
ответа ассистента добавляется та же форма части, что в 101-1, сразу в статусе `done` (здесь нет
`writer` и нет живой вкладки, которой стримить промежуточное `pending` — это ограничение, названо
заранее, а не найдено постфактум):

```
parts: [
  { text, type: "text" },
  { type: "data-parse-step", id: "model-answer", data: { id: "model-answer", label: "Модель сформировала ответ", status: "done" } },
]
```

## 2. Что считается готовым

Ответ, рождённый на входящее сообщение из Telegram, тоже несёт `data-parse-step` в `parts`.

## 3. Чем доказывается

- **SQL на сервере:** запрос к `Message_v2` на разговор тестового Telegram-бота, последний ответ
  ассистента — `data-parse-step` присутствует.
- **Негативный контроль:** ветка `fail()` (например, модель вернула ошибку) — в историю НИЧЕГО не
  сохраняется (уже существующий закон «отказ не сохраняется как ответ модели»), значит и
  `data-parse-step` там нет и не должно быть — проверяется тем же SQL на разговоре, где
  сознательно вызван отказ (например, временно снят ключ OpenAI).

## 4. На что опирается

101-1 — форма части должна быть той же.

## 5. Чего не входит

UI (101-3); синхронный стрим статуса `pending` — на этом пути его физически негде показать.
